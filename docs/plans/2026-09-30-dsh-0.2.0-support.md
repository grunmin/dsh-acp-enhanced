# Migration: dsh 0.2.0 support (host-side peer gate, additive line)

- Date: 2026-09-30
- Status: **implemented** — decisions §3.1 `0.10.0`, §3.3 floor `^0.2.0-rc.2`; every §5 row below
  carries the result actually measured, including the two negative controls
- Base: **`main`** (`0ef3357`, "fix(acp): close a stopped turn with a legal cancel cause")
- Scope: add the **0.2.0 line** to the supported range **without** dropping 0.1.5-rc.2 / 0.1.6-alpha.x
  / 0.1.7 — the same "dual line, one binary" policy as `2026-09-24-dsh-0.1.7-support.md`
- Supersedes nothing. The 0.9.x public-API rewrite and every earlier adaptation stand.

## 2. What actually breaks (measured, not inferred)

### 2.1 The host's own peer gate rejects this bundle on 0.2.0

`evaluatePluginCompatibility` (in `@deepseek-ai/dsh-plugin-manager`, called by
`@deepseek-ai/dsh-app-boot`) checks every `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` peer of a
bundle manifest with real semver:

```js
semver.satisfies(runtimeVersion, range, { includePrerelease: true })
```

Called directly against this repo's `package.json` in the 0.2.0-rc.2 closure:

| runtime | result |
| --- | --- |
| `0.2.0-rc.2` | **12 peers incompatible**, `exempted: false` |
| `0.1.7-rc.2` | `undefined` (compatible) |

A caret ceiling is emitted as `<0.2.0-0`, so `^0.1.7-alpha.1` does **not** contain `0.2.0-rc.2`
even with `includePrerelease: true`.

Consequences:

- **Boot path** — `loadProfileDirectory` catches the throw *per bundle*, drops that bundle's
  entire patch layer, and prints one stderr line via `reportSkippedBundles`:
  `dsh: skipping profile bundle "dsh-acp-enhanced": Plugin dsh-acp-enhanced@0.9.1 is incompatible
  with dsh 0.2.0-rc.2: peerDependencies {…}`. The process keeps running; the ACP transport is
  simply not there.
- **Install path** — `dsh plugin add` / the plugin manager raise a hard
  `incompatible-version` failure and ask for an exact-version exemption
  (`dsh plugin allow-version`) or a compatible plugin version.

On the maintainer's own `acp-enhanced` profile (4 non-base bundles), **3 would be skipped** on a
0.2.0-rc.2 CLI: `dsh-acp-enhanced` (12 peers), `dsh-free-search@0.4.39` (5), `dsh-mnemon@0.5.16`
(2). Only `dsh-notification@0.1.4` is peer-clean. The third-party two are **not fixable here**
(§7).

### 2.2 The bridge's own gate disagrees, so nothing warns

`scripts/lib/dsh-version.mjs`'s `isSupported` compares the version against a caret ceiling string
**without** semver's `-0` rule, so `0.2.0-rc.1`/`0.2.0-rc.2` are reported as **inside**
`^0.1.5-rc.2 || ^0.1.6-alpha.1 || ^0.1.7-alpha.1` (exit 0) while the host gate rejects them:

| version | bridge helper | host semver gate |
| --- | --- | --- |
| `0.1.7-rc.2` | supported | compatible |
| `0.2.0-rc.2` | **supported** | **incompatible** |
| `0.2.0` | unsupported | incompatible |

The launcher stays silent and the bundle is skipped upstream. Two gates that describe the same
claim must not disagree — that is a defect this migration fixes regardless of 0.2.0 (§3.5).

### 2.3 Link-time success is not boot-time success

This repo's own lesson from 0.1.7 (`resolveMountable`) applies verbatim: §1's clean import proves
only that no static export disappeared. The 0.2.0 degradation is a **host-side manifest gate**, so
only a real boot with a 0.2.0 CLI can certify the claim (§5 rows 10–13).

### 2.4 Widening the range is *not* enough — the install path also evaluates the bundle's rows

This was found by doing the thing rather than reasoning about it (E0): with the range already
widened, `dsh plugin --profile acp-ci-… add link:$PWD` on a clean, independently installed
`@deepseek-ai/dsh@0.2.0-rc.2` still failed:

```
dsh: installation rejected: Plugin @deepseek-ai/dsh-agent-presets@0.1.6-alpha.2 is incompatible
with dsh 0.2.0-rc.2: peerDependencies {"@deepseek-ai/dsh-agent":"^0.1.6-alpha.2", … "dsh-tools":"^0.1.6-alpha.2"}
… To accept this risk explicitly, grant the exact-version exemption … then retry
dsh: to accept the risk, run: dsh plugin --profile <p> allow-version … --accept-risk
dsh: plugin command failed; diagnostics: …/.plugin-manager/logs/operation-…/pnpm.log
```

The plugin manager validates more than the bundle's own manifest. `bundleComponentManifests`
(`dsh-plugin-manager/lib/index.js:404`) reads the bundle's patch files, collects **every row
`name`**, resolves each from the install anchor and the bundle directory, and runs the same
`evaluatePluginCompatibility` on each resolved package. Our patch ships a row named
`@deepseek-ai/dsh-agent-presets` — the ≤ 0.1.6 roster, `disabled` on every later line by the
generation gate — and the declaration of that package as a **peer** made pnpm install it into
every 0.2.0 profile, where it resolved to `0.1.6-alpha.2` (no release past 0.1.6 exists). The gate
therefore rejected the whole installation, on the boot path *and* the install path.

**Not every incompatible member blocks an install** (row 23): the rejection is about what is being
installed — the added package plus whatever its own rows and peers resolve to. With
`dsh-free-search@0.4.39` still in the profile, `dsh plugin --profile deg add link:$PWD` on
0.2.0-rc.2 exits 0, printing one warning per incompatible member and `dsh: it stays installed but
profile startup denies it until you grant an exemption for those exact versions`.

Optionality does not help: `peerDependenciesMeta: {…: {optional: true}}` is respected by npm, but
pnpm's `autoInstallPeers` (the profile default, and dsh's default) installs optional peers too —
verified by regenerating this repo's lockfile with the optional marker in place: the package still
landed in the tree.

The fix is to stop declaring it (§3.6): the package is a dependency of the *harness*, not of this
bundle, on every line where that roster exists.

## 3. Decisions

### 3.1 Dual line, one binary (floor unchanged)

Keep 0.1.5-rc.2 / 0.1.6-alpha.x / 0.1.7 working and add 0.2.0 in the same binary, exactly as
0.1.7 was added. No `lib/` behavioural change is currently required (§1, §2.3 caveat aside).

**Version number — maintainer's call:**

| option | precedent / consequence |
| --- | --- |
| `0.9.2` (patch) | follows 0.9.0 → 0.9.1, which added the 0.1.7 line as a patch. Under the standing release policy that means tag + npm publish only, **no GitHub release** |
| `0.10.0` (minor) | a new supported upstream generation plus user-visible compatibility/troubleshooting changes; earns a GitHub release |

Recommendation: **`0.10.0`**, because the declared support boundary and the README's compatibility
contract change — but `0.9.2` is the strictly precedent-matching option.

### 3.2 No `lib/` change is planned

Evidence in §1 (additive API, 0 service/event removals, clean static link). If §5 row 10 fails,
the fix lands in `lib/` and this section is rewritten with the measured failure — a link probe
must never be upgraded into a boot claim by assumption.

### 3.3 Peer range: `|| ^0.2.0-rc.2` on **every remaining** `@deepseek-ai/dsh*` peer

The host gate tests the running version against each declared peer range, so **every** entry must
accept `0.2.0-rc.2`. A single un-widened range keeps the whole bundle skipped, which is exactly how
this migration started. The measured 11-entry incompatibility is reproduced as a negative control
in §5 row 7.

Floor choice: `^0.2.0-rc.2` (strictest verified floor; also accepts `0.2.0` final). The house style
used the line's lowest prerelease in 0.1.7 (`^0.1.7-alpha.1`); here that would be
`^0.2.0-rc.1`, which was superseded within a day and is not covered by CI. Maintainer's call:
`^0.2.0-rc.2`.

### 3.4 The generation gate already handles 0.2.0 — do not add a boundary

`cordis.patch.yml` classifies by `major > 0 || minor > 1 || (minor === 1 && patch >= 7)`;
`0.2.0` satisfies `minor > 1` on the first term, and `@deepseek-ai/dsh-agent-preset-registry@0.2.0-rc.2`
exists. The four inlined preset declarations are byte-identical to `dsh-web-app@0.2.0-rc.2`'s, and
`dsh-base@0.2.0-rc.2` adds one row (`otel`) that this bridge does not touch. Only comments change.

### 3.5 Align the local version helper with semver's ceiling

`caretBounds()` must emit the **ceiling's own prerelease floor** (`0.2.0-0`, i.e. `-0` appended),
so that any prerelease of the ceiling version counts as *outside* the range — the rule the host
gate enforces. `compareVersions` already orders `0.2.0-rc.2 < 0.2.0-0`, so the fix is confined to
`caretBounds` plus tests; `dsh-version.mjs` must stay dependency-free (it ships in `files` and runs
inside the launcher).

Prototyped and measured (E0): a one-line change to `caretBounds` (`+ '-0'` on the ceiling) makes
the helper agree with `semver.satisfies(…, {includePrerelease: true})` for **all nine** boundary
versions in §5 row 1, under both the current range and the widened one. With the fix alone (range
not yet widened), the launcher correctly warns instead of staying silent on a 0.2.0 CLI — a valid
intermediate state if the range widening is deferred.

### 3.6 Drop the `@deepseek-ai/dsh-agent-presets` peer (do **not** declare the legacy roster)

The bundle's patch still ships the ≤ 0.1.6 roster row; the *declaration* goes away. The package is
the harness's own dependency on every line where that roster exists, and rows resolve from the
running CLI's installation anchor — the identical mechanism the sibling registry row has used since
0.9.1 without any declaration of its own. Measured (E0: `createRequire(<cli>/package.json)` on four
independently `npm install`ed CLIs):

| runtime | `@deepseek-ai/dsh-agent-presets` from the anchor | version / peers | `dsh-agent-preset-registry` from the anchor |
| --- | --- | --- | --- |
| `0.1.5-rc.2` | **resolves** | `0.1.5-rc.3`, peers `^0.1.5-rc.3…` (this line has no gate, so nothing checks it) | resolves |
| `0.1.6-alpha.2` | **resolves** | `0.1.6-alpha.2`, peers `^0.1.6-alpha.2…` — satisfied by the runtime | resolves |
| `0.1.7-rc.2` | **does not resolve** | — | `0.1.7-rc.2`, peer `0.1.7-rc.2` |
| `0.2.0-rc.2` | **does not resolve** | — | `0.2.0-rc.2` |

So on 0.2.0 there is nothing for the install path's row check to evaluate, and on ≤ 0.1.6 the row
still resolves from the CLI. Both halves are boot-verified in §5 rows 10 and 12 — including the
legacy roster's own error wording on 0.1.5/0.1.6 (`preset "…" not found (available: standard, ptc,
minimal, cordis)`), which is what proves the *legacy* row is the one that activated there, versus
the registry's `Unknown agent preset: …` on 0.1.7/0.2.0.

Rejected alternative: keep the declaration and hide the row name from the install checker (a
relative or expression `name` is skipped by `bundleComponentManifests`). That defeats a safety gate
whose verdict — "this package is incompatible with the running line" — is *true*, and it would leave
an unused 0.1.6-only plugin installed in every 0.2.0 profile.

The invariant this leaves behind, now enforced offline by `scripts/support-claim-test.mjs`: **every
declared peer must also be a devDependency of the pinned line**, i.e. the peer set describes the
closure `lib/` actually links against. A package that only a patch row needs is resolved from the
CLI, never declared.

### 5.1 Post-review correction (2026-10-01)

Rows 20–21 covered one third-party skip and one self-skip. Row 20 was recorded as a failure, but
that was the doctor's own misreport: the implementation that shipped treated any skip line as a
hard failure, so a boot that had answered `initialize`, opened a thread and stayed alive was
printed as `BOOT FAILED … the profile died (exit still running)`, and the `inactiveEntries` skip
handling was unreachable behind it. Row 21 (the self-skip) is a real failure — the bridge's own
layer is dropped, so no handshake ever arrives. A review reproduced the gap with a benign
third-party bundle (an empty patch nothing depends on) and then, in the same round, re-measured
row 20's profile itself (row 22). Corrected:

- the classifier moved to `scripts/lib/boot-classify.mjs`, where `diagnose` makes a crash
  signature outrank the skip (`classifyCrash` first, `manifestGate` only as the fallback) and
  suppresses the skip entirely when the caller reports `bootOk` — a working boot with a skipped
  bundle is now `BOOT OK` + `DEGRADED <n> inactive items`, confirmed by rerunning the benign
  reproducer;
- the doctor's post-handshake wording no longer prints "died (exit still running)" when the
  process is alive;
- `scripts/dsh-acp-zed.sh` gives the skip its own `gated` flag, so a skip line no longer consumes
  the launcher's single fatal-hint slot (a skip followed by a real loader failure now translates
  both), and its pre-boot warning says "outside the range" (below-floor *and* above-ceiling)
  instead of always "below the range";
- the "a skipped third-party bundle never settles / a profile carrying one is dead" claim is
  **retracted**, not qualified. Re-measured with an independent probe on the very profile it was
  recorded from, with and without a user row that configures the skipped bundle's entry (rows 20
  and 22): `initialize`, `session/new` and a prompt to the model call all succeed. The only skip
  measured to take a boot down is the self-skip. `boot-classify-test.mjs` pins the corrected `FIX`
  wording so the claim cannot creep back in;
- upstream's exact-version exemption is recorded (row 23): it lifts the skip for a bundle with no
  release on the new line, at the price the warning names;
- `scripts/boot-classify-test.mjs` (blocking CI) and new launcher cases pin all of the above.

## 6. Risks

- **The gate is host-side and version-shaped, not capability-shaped.** It compares the *runtime*
  version against the declared range, so the declaration is a promise about lines, not about
  behaviour. Widening it for a line that later diverges would silently un-block a broken
  composition — CI's per-line boot matrix is what keeps that honest.
- **A skipped bundle is not a failed boot.** The profile still starts; only stderr says what is
  missing. Row 10's stderr assertion is the cheapest guard against shipping that state.
- **The install path checks every patch row, not just the manifest.** `bundleComponentManifests`
  resolves every row `name` and gates the *whole installation* on the resolved package's own
  peers (§2.4). Consequence for any future row: a row naming a package that has no release on a
  supported line makes the bundle uninstallable on that line **even when the row is
  generation-gated off**. Prefer row packages the harness ships on every declared line, and never
  declare such a package as a peer.
- **The ≤ 0.1.6 roster row now depends on the CLI's own closure** (§3.6). That is how the sibling
  registry row has always worked and all four lines are boot-verified, but it is the one place where
  removing a declaration traded a hard install-time check for an assumption about the harness's
  dependency graph. If a future 0.1.x patch stopped shipping `@deepseek-ai/dsh-agent-presets`, that
  row would fail to import and take the profile down; the named lines are frozen, and rows 10–11's
  preset assertions would catch a regression.
- **0.2.0 is an RC.** Behavior may change before final; the declared range `^0.2.0-rc.2` already
  accepts `0.2.0`, so a final-release regression would arrive without a version-range change.
  Re-run §5 rows 10–14 on the final before promoting it.
- **`latest` moved.** Anyone running `npm i -g @deepseek-ai/dsh@latest` today already has 0.2.0-rc.2,
  where the 0.9.1-era bridge **cannot be installed at all** (`incompatible-version`). This migration
  is not cosmetic.
- **Rollback**: revert the release commit. No `lib/` change is involved, so the 0.9.1-era binary
  keeps serving 0.1.5→0.1.7 while 0.2.0 goes back to "install rejected / bundle skipped".

## 7. Follow-ups

- **Third-party bundles gate themselves.** `dsh-free-search@0.4.39` and `dsh-mnemon@0.5.16` declare
  0.1.x-only peers and are skipped on 0.2.0 no matter what this repo does. The README
  troubleshooting table names the symptom and the outs (wait for their release, pin the CLI to a
  supported line, or accept upstream's exact-version exemption). Do not "fix" it here. **Measured
  cost = that bundle's capability, not the profile** (rows 20 and 22): on 0.2.0-rc.2 the boot
  answered `initialize`, opened a thread and carried a prompt to the model call — with and without
  a user row configuring the skipped entry — and the doctor says `DEGRADED`. The earlier "the
  profile never settles" reading came from the doctor's own misreport and is retracted (§5.1); a
  capability the profile silently loses is still worth upgrading or removing the bundle for.
- **`dsh-notification@0.1.4` reads `turn/end`'s cancel cause unguarded** (see the 2026-09-30
  cancel-cause finding). 0.2.0's `TurnEndCancelCause` is unchanged — `{kind:'legacy'}` is not new —
  so the exposure is the same as on 0.1.7 and remains out of scope.
- **The canary job** is aimed at `alpha`, which is still 0.1.7-alpha.2; once it moves to the 0.2
  line the job re-verifies a supported line instead of warning about the next one. If upstream
  ever publishes a `next` line past 0.2.0, the canary should read `next` rather than `alpha`.
- **`abortedCancelCause` is still a closed union with `assertNever`** on 0.2.0 (verified in
  `dsh-agent-loop@0.2.0-rc.2`), so the `0ef3357` fix and its two regression scripts stay load-bearing.
  Re-check on each new generation.
- **The peer/row rule now has a guard, and it should be the first thing consulted when a line is
  added or a patch row is written**: a package may be declared as a peer only if it exists on every
  declared line (enforced by `support-claim-test.mjs`'s peer⊆devDependency check), and any row name
  must resolve compatibly on every declared line because the install path evaluates it (§6). The
  `frames*` generations in `compat-check.mjs` and the four-cell boot matrix are the mechanical half.
- **Consider reporting the `autoInstallPeers` interaction upstream**: `peerDependenciesMeta.optional`
  does not stop pnpm from installing a peer, which is what made a package the bridge never imports
  part of the install rejection. Not a bug in dsh, but worth a note in its plugin-authoring docs if
  they recommend optional peers for line-gated packages.
