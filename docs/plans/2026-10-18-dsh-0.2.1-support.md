# Migration: dsh 0.2.1 support (a declaration-only line, plus one measured drift)

Released as **0.11.0**. Like 0.10.0 this is a support-line release, but it is the first one whose
peer-range change **widens nothing**: `^0.2.0-rc.2` already contained `0.2.1-rc.2`, so the new
alternative is a *name* for a line the CI matrix and the link check now cover. Everything the
bridge links against is unchanged; one declaration was removed, and one real difference was found
upstream and is documented in §2.3 rather than absorbed.

Sources for this record: the npm registry (dist-tags and per-version manifests), the upstream
release bodies (`deepseek-ai/deepseek-harness` releases atom feed), the public
`compare/dsh-v0.2.1-rc.1...dsh-v0.2.1-rc.2` diff (619,410 bytes), the published tarballs of
`@deepseek-ai/dsh-llm-deepseek`, `@deepseek-ai/dsh-web-search-deepseek` and
`@deepseek-ai/dsh-web-app` for both 0.2.0-rc.2 and 0.2.1-rc.2, and the local runs in §5.

## 1. What upstream shipped

`0.2.1` is an **RC line**. As measured on 2026-10-18: `latest` was 0.2.0-rc.2, `next` was
0.2.1-rc.2 (published 2026-10-17T08:36:31Z; `0.2.1-rc.1` was 2026-10-17T03:17:24Z), `alpha` was
0.2.1-alpha.5.

**Correction (2026-10-22).** `latest` has since moved to 0.2.1-rc.2 (the registry's last
modification is 2026-10-19T06:29Z), so a default `npm i -g @deepseek-ai/dsh` now installs this
line. That changes nothing this record measured about upstream artifacts; it changes what those
artifacts reach — and it makes the persona-suffix defect a first-turn failure for anyone on a
default install, not a corner case.

The release bodies name exactly two new features in `v0.2.1-rc.2`, both DeepSeek-facing:

| Feature | What it is, in the published artifacts |
| --- | --- |
| DeepSeek-V4.1-Flash-1017 | a **client label** plugin: `@deepseek-ai/dsh-client-ui-deepseek-model-label-1017`, inserted as a row in `@deepseek-ai/dsh-web-app`'s `cordis.patch.yml` only (upstream ships an e2e test asserting the picker renders `DeepSeek-V4.1-Flash 1017`) |
| DeepSeek Search and Fetch APIs | the bundle row `web-deepseek-api` → `@deepseek-ai/dsh-web-deepseek-api`, inserted in **`@deepseek-ai/dsh-base`**'s `cordis.patch.yml` with `apiKeyEnv: DEEPSEEK_API_KEY`; it registers `deepseek-search-api` / `deepseek-fetch-api` and the web-search settings switch selects them in place of the default route |

**`v0.2.1-rc.1`'s release body contains neither.** Whatever the compatibility note asks for, the
1017 and Search/Fetch adaptations are in **rc.2** — so this repo's new alternative starts at
`^0.2.1-rc.2`, not `^0.2.1-rc.1`.

For the bridge's own surface, the diff between the two RCs touches **`package.json` files only**
across `packages/llm/*` (which is where `llm-pi-ai` and the DeepSeek LLM adapters live). Confirmed
at the tarball level: `@deepseek-ai/dsh-llm-deepseek` 0.2.1-rc.1 vs 0.2.1-rc.2 differ in
`package/package.json` alone; `@deepseek-ai/dsh-web-search-deepseek` differs in `lib/index.js`,
`lib/types/provider.d.ts` and its READMEs (the Messages-search provider, not a surface this bridge
touches).

## 2. What actually breaks (measured, not inferred)

### 2.1 Nothing in the peer range — and that is the point

`^0.2.0-rc.2` expands to `>=0.2.0-rc.2 <0.3.0-0`, which contains `0.2.1-rc.2`. Every
`@deepseek-ai/dsh*` peer in 0.10.0 already accepted this line, and so does the host's own gate
(`evaluatePluginCompatibility`), which is the only consumer of those ranges. Measured: `compat`
link probe and a real boot both pass with the *old* package.json, and pass again with the new one
(§5).

So this line needed no widening, no `lib/` change, no new patch row, and no new generation-gate
boundary. The release exists so that the line is **stated and booted** instead of being admitted by
accident — an unstated line is one `scripts/support-claim-test.mjs` cannot hold.

### 2.2 What does change: the closure

`@deepseek-ai/dsh-invariants` has **no 0.2.1 release** (`next` stops at 0.2.0-rc.2) and
`@deepseek-ai/dsh@0.2.1-rc.2` no longer depends on it. It was a 0.10.0 peer — a version-tracking
declaration, never imported by `lib/` and never a patch row — so on this line it is a declaration
for a package the line does not have. Measured locally: a fresh `pnpm install` resolves zero
`dsh-invariants` entries once the declaration is gone (§5 row 2).

### 2.3 What does change: the host's preset compositions (the finding of this release)

The bridge **inlines** the four agent-preset declarations (`standard`, `ptc`, `minimal`, `cordis`)
because the ACP profile does not carry `@deepseek-ai/dsh-web-app`, whose `presets/*.patch.yml`
is upstream's source of truth. 0.10.0 could state that the inlined set was byte-identical to
`0.2.0-rc.2`'s. **It is no longer identical to `0.2.1-rc.2`'s.** All four files differ; `standard`
and `minimal` differ substantively:

| Upstream change, 0.2.0-rc.2 → 0.2.1-rc.2 | Effect on the bridge's inlined copy |
| --- | --- |
| `persona.config.suffix: Your working directory is {{cwd}}.` **removed** (and `cwd` left the variable registry) | bridge passed `suffix` at 0.11.0 — **not a fidelity gap but a turn failure**; dropped in the follow-up below |
| new row `time-context` (`@deepseek-ai/dsh-time-context`) | absent from the bridge (the package exists on **all four** lines) |
| new row `tool-schedule` (`@deepseek-ai/dsh-tool-schedule`) | absent (the package exists on **0.2.1 only**) |
| new row `tool-plugin-market` (`@deepseek-ai/dsh-plugin-market/tools`, `disabled: true`) | absent (0.2.1 only) |
| plan-mode `section` reworded (`exit_plan_mode succeeds` → `the user approves your plan through exit_plan_mode`) | bridge ships the 0.2.0 wording |
| `backgroundMode: continuable` **removed** from `tool-subagent` and `tool-subagent-fork` | bridge still passes it |
| rows `tool-subagent-codex`, `tool-subagent-claude-code`, `tool-ralph` removed | bridge still declares them (`disabled: true`; `@deepseek-ai/dsh-tool-ralph` still exists on all four lines) |
| `minimal` gains `tool-fs` (`readImage` only) and a `compaction` group (`compaction-basic` + `command-compact`) | absent from the bridge's `minimal` |

Consequence, stated plainly: on a 0.2.1 host an ACP user gets the **0.2.0 composition** — no
`time-context`, no `tool-schedule`, no `minimal`-preset compaction, and the 0.2.0 plan-mode text.
This is a fidelity gap, not a boot failure, and it is *not* user-invisible.

Why it is documented rather than fixed in this release is §3.7; the evidence is the same table —
two of the new rows name packages that exist on 0.2.1 only, and the install path evaluates **every
patch row's `name`**, so a row the older lines cannot resolve is a risk to `dsh plugin add` there,
not just a disabled line (§6 of the 0.2.0 record).

**Follow-up (2026-10-22).** One row of that table was never a fidelity gap: the removed `{{cwd}}`
clause is a *turn* failure, not a composition difference. The variable was registered by
`dsh-agent-loop` on every line through 0.1.7 (`lib/index.js:1551` in 0.1.7-rc.2) and is simply
absent on 0.2.1-rc.2, which registers only `provider` and `model` (`lib/index.js:1591-1592`).
`dsh-system-prompt` interpolates strictly, so the bridge's persona suffix failed prompt assembly
for every session with `unknown prompt variable "{{cwd}}"` — boot succeeded, mount succeeded,
every turn died. The keyless smoke cannot catch it: it opens a session and never assembles a
turn, which is how the 0.11.0 board went green with the defect in it. The three rosters that
declared a persona (`standard`, `ptc`, `cordis`) and the reference `profile/cordis.yml` now drop
the suffix and keep only the model prefix.

Where the directory then comes from is line-dependent, measured on 2026-10-22:

| line | `cwd` prompt variable | `working-directory` row in `dsh-base` | single-root session |
| --- | --- | --- | --- |
| 0.1.6-alpha.2 | registered (`dsh-agent-loop` `lib/index.js:1535`) | absent | **loses the sentence** |
| 0.1.7-rc.2 | registered (`:1551`) | absent (package not published on that line) | **loses the sentence** |
| 0.2.0-rc.2 | registered (`:1566`) | absent (no such row) | **loses the sentence** |
| 0.2.1-rc.2 | gone | present — emits `Current working directory: …` | host supplies it |

So the removal is lossless on 0.2.1 and costs one sentence on the other three. Multi-root
sessions keep the directory through this bridge's own `acp:workspace-roots` context, which is
empty when there are no extra roots. Gating the sentence by version was rejected: three `!!js`
`installAnchor` probes on the boot path (the mechanism the roster gate already uses) for one
sentence, against a model that can read its directory with `pwd`.

The rest of the table still stands as a fidelity gap. Nothing offline guards the turn itself: no
script in this repo composes a preset, so the first guard that can see a recurrence is the keyed
e2e leg of the 0.2.1 matrix — a keyless boot cannot, and neither can this record.

## 3. Decisions

### 3.1 Name the line even though the alternative narrows nothing

The peer range doubles as the list of lines this bridge claims, and
`scripts/support-claim-test.mjs` requires **every** alternative to have a CI matrix version and a
`compat-check` generation. Adding `|| ^0.2.1-rc.2` is therefore the mechanism that puts a boot
behind the new line; leaving it out would keep 0.2.1 admissible while unverified, which is exactly
the state the guard was written to prevent.

### 3.2 The alternative's floor is `rc.2`, not `rc.1`

The adaptations that motivated the line (§1) are in rc.2, and rc.2 is what §5 boots. A floor of
`^0.2.1-rc.1` would claim a version this repo has not run — `^0.2.1-rc.2` claims exactly what was
verified and still covers every later `0.2.x`.

### 3.3 No `lib/` change

Nothing the bridge imports moved: `packages/llm/*` changed by `package.json` only across the RCs,
and `compat-check` links the bridge against the 0.2.1 closure. No member probe, no row, no
generation boundary.

### 3.4 `@deepseek-ai/dsh-invariants` leaves `peerDependencies` **and** `devDependencies`

It never existed as a consumed surface here (not imported by `lib/`, not a row), it has no release
on the new line, and a declared peer is installed into every profile that carries the bundle — the
same reasoning that removed the ≤ 0.1.6 roster package in 0.10.0. The guard's
peer ⊆ devDependency invariant stays satisfied because both sides drop it together.

### 3.5 No new generation-gate boundary

The gate reads `profileContext.installAnchor`'s version and enables the registry roster for
`major > 0 || minor > 1 || (minor === 1 && patch >= 7)`. `0.2.1` satisfies `minor > 1`, so it
classifies as a registry line without a change — the same way 0.2.0 did.

### 3.6 `framesRegistry021` pins the line *without* `dsh-invariants`

The generation's `deps` reproduce what the CLI resolves (the cordis trio at `~4.0.5` /
`~1.0.10` / `~1.0.6`, the eleven harness packages at `0.2.1-rc.2`, the roster at
`@deepseek-ai/dsh-agent-preset-registry`). A generation that kept installing `dsh-invariants`
would prove a closure the line does not have — the reason it is absent there while the 0.2.0
generation keeps it.

### 3.7 The preset drift is accepted for 0.11.0, with the evidence recorded

Adopting 0.2.1's compositions would mean inlining rows whose packages do not exist on the older
declared lines (`tool-schedule`, `plugin-market`) into a declaration set that is shared by **all
four** lines, and re-verifying the install path on each. That is a larger change than this release,
it is not needed for the line to boot (§5 row 6 composes presets successfully on 0.2.1), and doing
it blind would trade a documented gap for a possible `dsh plugin add` regression on 0.1.6/0.1.7/
0.2.0. §7 carries it forward with the availability data needed to decide it properly.

### 3.8 Release history moves out of the READMEs, and a guard keeps it there

The READMEs had grown four per-release sections ("What 0.9.0 changed" … "What 0.11.0 changed"),
which is release history living on the page a new user reads first — and, for part of it, the only
place it lived. It is now `CHANGELOG.md` (Keep a Changelog shape, newest first, one entry per
version, each leading with a one-line summary and linking to its migration record) with
`CHANGELOG-zh.md` as the mirror the bilingual convention calls for; the READMEs keep the
*compatibility* surface and point at the changelog. Two consequences worth naming:

- the support-policy table's per-release cells lose their narrative. That table answers "which
  lines does this bridge claim", not "what changed in it". The prose moved to the changelog
  **verbatim** (headings only demoted), so nothing was rewritten and nothing lost in the move;
- a document no guard reads can rot, which is how 0.10.0 shipped stale README facts.
  `scripts/docs-claim-test.mjs` now pins the structural half: both READMEs quote the manifest's
  peer range; each changelog's newest entry is `package.json`'s version; both changelogs list the
  same versions in the same order; every released version in the support table has an entry;
  release history stays out of the READMEs; and the two languages agree on heading count. It was
  **negative-tested** rather than only run green — a bumped manifest, a re-added history heading, a
  dropped range and a deleted changelog entry each fail the check that should catch them.

## 6. Risks

- **The new alternative admits nothing.** A reader can mistake the range for what lets 0.2.1 boot;
  it is `^0.2.0-rc.2` that does, and the alternative's only mechanical effect is to add a CI cell
  and a link generation. Documented here and in the CI comment so nobody "narrows" it later.
- **The preset drift is real and user-visible** (§2.3). It is not a boot failure, and the smoke
  proves the composition mounts; but a 0.2.1 user does not get `time-context`, `tool-schedule`, or
  the new `minimal`-preset compaction, and the plan-mode prompt text is the older one. Accepted for
  this release (§3.7) and carried in §7.
- **`backgroundMode: continuable` is still passed** where upstream 0.2.1 dropped it from
  `tool-subagent`/`tool-subagent-fork`. It is accepted on 0.2.1 (row 6), but whether upstream's
  removal was cosmetic or semantic is unverified here — worth a look before 0.2.1 stops being an
  RC.
- **The roster package's public surface shrank** (9 → 6 exports on `dsh-agent-preset-registry`,
  row 4). Nothing this bridge imports is gone — `compat-check` and `api-surface-check` both pass —
  but the package is a declared peer, so a future release that removes `resolve` would be a
  link-time break on the newest line only.
- **Dropping the `dsh-invariants` declaration** is only safe because the package is unused by
  `lib/` and by every patch row. Should a future change start importing it, the peer has to come
  back *and* a line-independent source has to exist for it.
- **Rollback**: revert the release commit (it carries the lockfile). No `lib/` change is involved,
  so the 0.10.0 binary keeps serving 0.1.6 → 0.2.0 while 0.2.1 goes back to being admissible but
  unclaimed.

## 7. Follow-ups

- **Decide the preset drift.** The data needed is §2.3 plus availability: `@deepseek-ai/dsh-time-context`
  exists on all four declared lines; `@deepseek-ai/dsh-tool-schedule` and
  `@deepseek-ai/dsh-plugin-market` exist on 0.2.1 only; `@deepseek-ai/dsh-tool-ralph` still exists
  on all four (upstream merely stopped declaring it). The options, in order of cost: (a) accept the
  0.2.0 composition on every line; (b) adopt the line-independent parts (`time-context`, the
  reworded plan-mode section, the `backgroundMode` removal — the `suffix` half is already done,
  out of necessity rather than choice: see the §2.3 follow-up) and keep only the 0.2.1-only rows
  out; (c) move to per-line preset declarations behind the existing version gate,
  which additionally requires proving the install path on all four lines for the new row names.
  Whatever is chosen, the inlined set's header comment should stop claiming byte-identity with
  `0.2.0-rc.2` as if it were current.
- **Re-run §5 rows 5–8 on the final 0.2.1**, as 0.10.0's record required for 0.2.0: the range
  `^0.2.1-rc.2` already accepts a final `0.2.1`, so a final-line regression would arrive without a
  version-range change.
- **The canary** now watches `alpha` = 0.2.1-alpha.5, which is inside the declared range, so the
  job re-verifies a supported line. It becomes a real early warning again when upstream publishes
  the line after 0.2.1 under `alpha`; the comment records the current tags.
- **`@deepseek-ai/dsh-invariants`** should be watched for a late 0.2.1 release: if one appears, the
  peer's removal can stay as-is (nothing imports it), but the compat generation for this line would
  then be describing a closure upstream does ship again.
- **The peer/row rule from 0.10.0 held up** and was the reason §3.7 was not attempted blindly:
  a package may be declared as a peer only if it exists on every declared line, and any row name
  must resolve on every declared line because the install path evaluates it.

## 8. Left to the maintainer

- **A real Zed session on 0.2.1-rc.2.** Everything in §5 is a driver or an offline guard; none of
  them exercises Zed's own client behaviour (slash-command validation, elicitation, terminal
  panels), and §2.3's drift is most visible there — a `standard`-preset session will not show the
  `time-context` row's context or offer `tool-schedule`.
- **The model-backed legs** (`acp-client.mjs`, `acp-message-fallback-test.mjs`,
  `acp-resume-test.mjs`, `acp-client-tools.mjs`): CI runs them per matrix cell when
  `DEEPSEEK_API_KEY` is present. Do not promote the final `0.2.1` on the keyless legs alone.
- **The release itself**: version 0.11.0 is a feature release under this repo's policy (a new
  supported line), so it expects a tag, a push and a GitHub release in addition to
  `npm publish` — no remote write has been performed as part of this record.
