# Migration plan: dsh 0.1.2-alpha.2 support with back-compat to ≤0.1.1-rc.2

- Date: 2026-09-01
- Status: implementing (branch `feat/dsh-0.1.2-alpha.2-support`)
- Scope: this package (`dsh-acp-enhanced`) adapts to DeepSeek Harness
  `0.1.2-alpha.2` while staying loadable and correct on every harness
  generation from `0.1.0-rc.6` through `0.1.2-alpha.2`.

## 1. Background

DeepSeek Harness 0.1.2-alpha.1/.2 rewrote two APIs this bridge consumes
(verified by diffing the published npm tarballs of 0.1.0-rc.6 vs
0.1.2-alpha.2, and by an empirical import probe):

| API | ≤ 0.1.1-rc.2 (legacy) | ≥ 0.1.2-alpha.2 (projection) |
| --- | --- | --- |
| running preset of a session | `resolveSessionPreset({ header, events })` export of `@deepseek-ai/dsh-agent-presets` | export removed; state lives in the `agentPreset` session projection (`sessionProjections.stateOf(session, 'agentPreset')`) |
| preset resolution failure | `UnknownPresetError` / `PresetMountError` (named exports) | `RemoteError` with codes `agent-preset/not-found` / `agent-preset/invalid` |
| `permissionPresets.current(x)` | `current(events)` — folds the event array | `current(session)` — reads the `permissions` session projection via `permissionState(session)` |

Under 0.1.2-alpha.2 the package's static named import of the removed exports
fails at ESM link time, so the bridge cannot even load:

```
SyntaxError: The requested module '@deepseek-ai/dsh-agent-presets'
does not provide an export named 'PresetMountError'
```

Everything else this bridge touches was verified unchanged across both
generations: `createUserMessage` / `errorChain` / `ReasoningEffortId`
(dsh-llm), `installModelSelection` (dsh-agent), `renderSkillContent`
(dsh-skill), `defineTool` (dsh-tools), `SessionId` (dsh-session),
`agents.create/resume` option shapes, `AgentPresets.resolveMountable/mount/
serviceFor`, every listened event (`agent/inbox/spliced`,
`llm/adapters-updated`, `session/event`, `session/title`, `tool/call`,
`tool/result`), the session event vocabulary (additions only), the profile
row set of the dsh-base patch (additions only), the sqlite query engine
(byte-identical), the MCP client Config schema, and `persistence.load() →
{ meta, events }`.

## 2. Architecture decisions

### 2.1 Pure helpers are copy-safe; service identity is not

Runtime module resolution in this deployment (verified 2026-09-01):

- The dsh CLI symlinks its whole dependency closure into
  `$DSH_HOME/profiles/node_modules` (shared by every profile under that home)
  on each boot. The base rows of a profile resolve their packages there, so
  **the booting CLI decides the service generation**.
- This package is `link:`-ed from the repo, so **its own static imports
  resolve the repo's `node_modules`** (devDependencies) first.

Two module copies therefore coexist whenever the repo pin and the booting CLI
disagree. The migration rules (validated against the openma
`deepseek-harness-acp` adapter's `self-harness.ts`, which states the same
invariant):

1. Value-import **pure helpers only** (no service identity):
   `createUserMessage`, `errorChain`, `ReasoningEffortId`, `SessionId`,
   `defineTool`, `renderSkillContent`, `installModelSelection`. A foreign copy
   of a pure function is functionally equivalent.
2. Never rely on cross-copy `instanceof` for service-thrown errors. Identify
   preset failures structurally (see 2.3).
3. When an API differs per generation, probe the **service instance**
   (whose generation is the booting CLI's), never this package's imports.

Consequences: no host-tree indirection module is needed, and the same
checkout runs under both old and new hosts — which is also the back-compat
requirement.

### 2.2 Running preset: one version-agnostic fold

Both generations define the running preset identically — the old
`resolveSessionPreset` and the new `agentPreset` projection agree field for
field: start from `header.agentPreset ?? null`, then the last
`agent-preset/selected` event's `data.agentPreset` wins. The bridge now folds
that itself (no import, no projection service, works for live
`agent.session` objects and for `{ meta, events }` read from persistence).

### 2.3 Preset failures: three-way identification

`isPresetClientError(error)` maps "client-side setup mistake" failures to ACP
`invalid params`:

1. ≥ 0.1.2-alpha.2: duck-typed RemoteError — `error.isDSHRemoteError === true`
   and `error.code` starts with `agent-preset/`. (Duck-typed because the
   class lives in the host tree and must not be imported.)
2. ≤ 0.1.1-rc.2: structural — both legacy classes carry `presetId`.
3. Same-copy `instanceof` against the namespace-imported classes, guarded for
   their absence (belt and braces for deployments where copies align).

### 2.4 permissionPresets.current(): service-instance probe

The bridge centralizes every `current()` read in
`currentPermissionMode(permission, session)`:

- `typeof permission.permissionState === 'function'` (new-generation-only
  method) → `permission.current(session)`
- otherwise → `permission.current(session.events)`

Passing the wrong argument shape to either generation does not throw
reliably — the projection path can silently return the default state — so
the probe is mandatory, not defensive.

### 2.5 Isolated DSH_HOME for the acp profile

`$DSH_HOME/profiles/node_modules` flips to the closure of the CLI that booted
last. Running the acp profile with the repo-pinned 0.1.2-alpha.2 CLI under
the default home would leave a running `dsh web` (0.1.0-rc.6) able to
lazily resolve 0.1.2-alpha.2 modules inside its own process. Therefore:

- The launcher resolves the dsh CLI as `DSH_PATH` → repo-pinned
  `<repo>/node_modules/.bin/dsh` → global `dsh` (legacy fallback).
- When the pinned/explicit CLI wins, the launcher exports
  `DSH_HOME=${DSH_ACP_HOME:-$HOME/.dsh-acp}` — a dedicated home whose
  fallback dir only ever sees 0.1.2-alpha.2. The global install and the web
  profile are untouched.
- The global fallback keeps the default home and the existing profile, so a
  fresh clone without `pnpm install` degrades to today's behavior.

The bootstrap script creates the isolated-home profile once: `dsh plugin add`
the repo link, verify the `bundles` array (`@deepseek-ai/dsh-base` +
`dsh-acp-enhanced`, **no** `dsh-mnemon` — decision 2026-09-01, dsh-mnemon
0.2.16 does not support 0.1.2-alpha.2), copy credentials, share the user
agent-preset root via symlink, port the home-level `cordis.patch.yml` if
present, and seed the effort-memory file.

## 4. Verification matrix

1. `node scripts/compat-check.mjs` — link-time import of the bridge against
   the 0.1.0-rc.6 and 0.1.2-alpha.2 generations from scratch installs.
2. E2E via `scripts/acp-client.mjs` against the isolated-home profile on the
   pinned 0.1.2-alpha.2 CLI (primary): initialize → session/new (modes and
   options advertised) → prompt (block streaming + usage telemetry) →
   `session/set_mode` (permission-preset path) → `/preset` listing (preset
   composition path) → `session/load` resume (persistence fold path).
3. E2E against the legacy host (global 0.1.0-rc.6 CLI, default home profile)
   — the same checkout must keep working there (back-compat path).
4. Manual Zed smoke on the new profile.

## 5. Risks and rollback

- The repo's devDependency bump makes **new** Zed sessions on the old profile
  a genuine cross-generation run (repo copies new, host services old). That
  is precisely the supported configuration per 2.1–2.4; E2E case 3 covers it.
- Rollback: `git checkout main` in the repo and re-run `pnpm install`; the
  old profile at `~/.dsh/profiles/acp-enhanced` is left untouched by design,
  so the pre-migration setup keeps working unmodified.
- The isolated home (`~/.dsh-acp`) is additive; removing it restores the
  default-home behavior exactly.

## 6. Implementation log (2026-09-01, all verified)

Discoveries made while landing the plan:

1. **The devDependency set had to become ranges, not exact pins.** The pinned
   `@deepseek-ai/dsh@0.1.2-alpha.2` CLI declares `^0.1.2-alpha.2` on its 61
   harness packages, and 0.1.2-alpha.3 (published after the assessment)
   satisfies those ranges — so a fresh install resolves an alpha.3-family
   closure. Exact alpha.2 top-level devDeps next to that closure produce a
   split tree (two versions per name) and the profile heal — a BFS that links
   the first resolvable instance per name — then boots a mix that fails with
   export-not-found (`assertNever`, `ImageVariantId`). devDeps now mirror the
   CLI's own ranges so one coherent family resolves; a clean reinstall
   (`rm -rf node_modules && pnpm install`) is mandatory after changing them
   (stale .pnpm store entries poison the heal BFS). `pnpm-workspace.yaml`
   approves the CLI closure's build scripts (node-pty prebuilds, koffi) —
   the repo CLI boots real profiles, so they are runtime requirements.
2. **The 0.1.2-alpha `standard` preset requires a host-scope service that
   dsh-base does not provide.** It mounts tool-subagent with
   `modelSelectionSettings: true`, which requires `subagentModelSelection`
   (from `@deepseek-ai/dsh-tool-subagent/model-selection-settings`) in the
   Host scope; only dsh-web-app mounts it for the web profile. Pre-0.1.2
   harnesses do not export the module, so the row cannot ship in the
   version-agnostic bundle patch — `scripts/init-acp-home.sh` writes it into
   the isolated home's user layer instead.
3. **Ambient `DSH_HOME` must be overridden, not honored.** dsh exports
   `DSH_HOME=$HOME/.dsh` into every child process of a harness session; the
   launcher initially honored an exported `DSH_HOME`, so the repo CLI booted
   the profile against the DEFAULT home and healed its shared closure to the
   alpha family once (detected and reverted within minutes; the running web
   process kept its loaded modules). The launcher now overrides an inherited
   `DSH_HOME` that merely points at the default home; only a non-default
   value is respected as user intent.
4. **Privacy: the 0.1.2-alpha base patch mounts
   `plugin-package-inventory-deepseek` (plugin names + versions attached to
   official DeepSeek requests) with `enabled=true` by default.** The
   bootstrap user layer disables it (red line: no third-party reporting).
5. **Migration set**: credentials + settings.yaml (the pi-ai provider
   profiles and the saved default route live there), the user-layer patch
   (web-search routing), the effort memory, the agent-preset user root —
   all handled by `scripts/init-acp-home.sh`, never overwriting existing
   files.
6. **Session storage is `$DSH_HOME/sessions/<slug>/<id>/session.jsonl.zstd`
   on BOTH generations** (the earlier "cwd `./.sessions`" belief was stale),
   and the new generation reads old-generation logs: cross-generation
   `session/load` verified (history replay + preset fold). Old Zed threads
   become resumable by copying the old home's session history;
   `init-acp-home.sh --copy-sessions` does it, nothing is copied by default
   (the default home's tree also holds every web-profile session).
7. **The 0.1.2-alpha credentials service migrates a flat credentials file to
   a version-1 `refs` layout on boot** (values preserved verbatim) — a
   layout the 0.1.0-rc.6 parser rejects. The flip-window boot rewrote the
   DEFAULT home's `~/.dsh/.credentials.yaml` this way; restored to the flat
   layout and re-verified with the keyless smoke. With the launcher fix,
   new-gen boots only ever write the isolated home's copy.

8. **The `userQuestions` registration seam was ALSO rewritten by 0.1.2-alpha
   (missed in §1's diff — the plan's API table only covered agent-presets and
   permissionPresets).** The legacy `UserQuestionService` exposes
   `registerProvider({ ask })` (single active provider); the projection
   generation removed that method and asks answerers to listen on the
   `user-questions/request` Cordis waterfall instead (claiming a request by
   returning an answer, or delegating via `next()`). The bridge previously
   called `userQuestions.registerProvider(...)` unconditionally — on the new
   host `ctx.get('userQuestions')` is still defined (service mounted by the
   dsh-base bundle row), so the old guard passed and the missing method
   threw `userQuestions.registerProvider is not a function`, surfacing in Zed
   as an `Internal error` on initialize. Fixed in `lib/index.js` by probing
   the service instance (migration plan rule 2.1.3): `registerProvider` when
   present, otherwise a root `ctx.on('user-questions/request', ...)` listener
   that answers bridge-owned requests and delegates everything else via
   `next()`. Verified both ways: the buggy code reproduces the exact Zed
   error on the isolated home; the fixed code passes initialize with form
   elicitation and the full `acp-client-tools.mjs` elicitation suite on the
   new host, and the same suite still passes on the legacy host.
