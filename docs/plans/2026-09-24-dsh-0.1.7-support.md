# Migration: dsh 0.1.7 support (agent-preset roster repackaging)

- Date: 2026-09-24
- Status: executed — bridge **0.9.1**, floor unchanged at **0.1.5-rc.2**
- Base: **`main`** (`38227eb`). The unpublished review-fix commits on `fix/review-fixes`
  (link-check CI step, `session-facts-test`, lib fold fixes) are **not** included, and this
  migration does not depend on them; every row of §5 was re-run on this base.
- Scope: add the 0.1.7 line to the supported range **without** dropping 0.1.5/0.1.6
  (the `0.9.x` line keeps serving all three)
- Supersedes nothing; the 0.9.0 public-API rewrite and the 0.1.3+ adaptation stand

## 1. What upstream shipped

`npm dist-tags @deepseek-ai/dsh` at the time of writing:

| tag | version |
| --- | --- |
| `latest` | 0.1.5-rc.3 |
| `alpha` | 0.1.7-alpha.2 |
| `next` | 0.1.7-rc.2 |

The 0.1.7 line is the first since 0.1.3 with a **structural** change to a surface this bridge
consumes:

| Thing | ≤ 0.1.6 | ≥ 0.1.7 |
| --- | --- | --- |
| agent-preset roster package | `@deepseek-ai/dsh-agent-presets` (last release 0.1.6-alpha.2) | `@deepseek-ai/dsh-agent-preset-registry` — nothing depends on the plural name any more |
| service | `ctx.agentPresets` (`AgentPresets`) | `ctx.agentPresets` (`AgentPresetRegistry`) — **same service name and config key** |
| shipped presets | bundled in the roster package, prepended as a read-only `system` root (`includeShippedRoot`) | one `@deepseek-ai/dsh-agent-preset` **declaration row** per preset; `dsh-web-app` ships them as `presets/*.patch.yml` bundle layers, and `dsh.bundle.patch` became an **array** there |
| `AgentPreset` row shape | `{id, trust, path, name?, description?, order?, broken?}` | `{id, name?, description?, order?, broken?}` — the `broken` verdict is still published |
| roster members | `list resolve resolveMountable mount recompose composedPreset composeFrom read readDocument copy remove select serviceFor` | `list resolve mount recompose composedPreset composeFrom readDocument select serviceFor register defaultId remoteExportList acquireScope compositionInventory` — `resolveMountable`/`read`/`copy`/`remove` are gone |
| `resolve()` on a broken preset | refuses (that is what the private `resolveMountable` was for) | returns it on purpose; every *mounting* path refuses after resolution |

Two further 0.1.7 facts that shaped the work:

- **`dsh-base` row set moved** (+`authorization`, `config-editor`, `deepseek-account`,
  `llm-deepseek-account`, `image-offload`, `mcp-resources`, `plugin-manager`, `ptc-runtime`,
  `tool-plugin-manager`, `workflow-ptc`; −`workflow-worker-thread`). The bridge's disable list
  already matched the web-app patch apart from the known `command-goal` exception, so **no row
  list change was needed**.
- **A boot-time peer gate is new** (`evaluatePluginCompatibility`): a profile bundle whose
  `@deepseek-ai/dsh*` peers do not satisfy the runtime is rejected unless the profile's
  `compatibility.json` grants an exact-version exemption. The bridge's declared ranges already
  covered 0.1.7 through `^0.1.5-rc.2` (caret ceiling 0.2.0), so no exemption is involved — but
  the range is now declared explicitly (below) rather than accidentally.

## 2. What actually broke (measured, not inferred)

1. **The link probe would have declared victory.** `scripts/compat-check.mjs` imports the
   bridge from a scratch resolution root; every static import still resolved on 0.1.7. Only a
   real boot exposes this migration — the same lesson as the 0.1.5 persistence redesign.
2. **Boot succeeds, degraded.** The bundle patch's `name: '@deepseek-ai/dsh-agent-presets'`
   insert fails to import on 0.1.7 (`dsh: warning: 1 entry did not activate … failed to
   import`), the loader continues, and `session/new` opens a thread — but with no roster:
   no `agent_preset` config option, no `/preset` roster, and `plan_mode` missing because 0.1.7
   owns it inside presets. This is what "the bridge runs on 0.1.7 today" actually means.
3. **With a roster mounted, `session/new` fails**: `presets.resolveMountable is not a
   function` (probe: a `@deepseek-ai/dsh-agent-preset-registry` row inserted into a scratch
   profile). That is the one consumed member 0.1.7 removed.
4. **The probe rows resolve from the installation.** A row naming
   `@deepseek-ai/dsh-agent-preset-registry` / `@deepseek-ai/dsh-agent-preset` activates in a
   profile that does not contain them: 0.1.7's loader resolution table serves
   installation-scope packages to plugin specifiers.
5. **The first gate design then broke the 0.1.6 line** — see §3.2.1. It is recorded here
   because the failure only became visible after the repo's own devDependencies moved to 0.1.7,
   i.e. a later step of this same migration.

## 3. Decisions

### 3.1 Dual line, one binary (0.9.1, floor unchanged)

The maintainer's call: keep 0.1.5/0.1.6 working and add 0.1.7 in the same `0.9.x` release,
rather than publishing a 0.10 that drops the older lines. 0.1.7 is a repackaging, not a new
declared API surface — the frames seam, the services, the events and every static import are
unchanged — so it does not earn a floor move, and `latest` (0.1.5-rc.3) users are not stranded.

### 3.2 The generation gate reads the booting installation's identity

Both roster rows ship in `cordis.patch.yml`, each with a `disabled` expression; exactly one may
activate because they provide the **same service name** (a second `provide()` throws). The gate
cannot live in `name:` or `config:` — a `name:` that resolves to nothing is a hard import
failure, while a **disabled row is never imported** (`Entry._disabled` short-circuits before
`init()`).

`!!js` expressions are evaluated `with (ctx) { eval(expr) }` over the loader context plus
globals, so no harness version is in scope. The gate therefore opens
`profileContext.installAnchor` — the running CLI's own `package.json`, a fixed path inside the
installation whose `version` names the closure whose roster package the loader will import:

- no `profileContext` at all (0.1.5 does not register the service) → the `≤ 0.1.6` row,
- `0.1.6-alpha.2` → the `≤ 0.1.6` row,
- `0.1.7-rc.2`, anything above 0.1.7 on the 0.1.x line, or a later major → the registry rows.

`profileContext` is registered by the profile-boot `prepare` callback, which `boot()` runs
**before** mounting the plugin tree, so the gate never races it. Everything unreadable,
unparseable or unexpected keeps the older row — the graceful degradation described in §2.2,
never a boot failure. `process.getBuiltinModule('node:fs')` keeps the read in scope (Node
≥ 22.3; a host without it throws into the catch).

### 3.2.1 The first cut was wrong (recorded)

The gate started as a resolver probe, mirroring the 0.1.5-era "probe the service instance"
instinct:

```js
ctx.get('pluginPackages').packageOf('@deepseek-ai/dsh-agent-preset-registry', <profile package.json URL>) !== undefined
```

It passed on 0.1.5 and 0.1.7, and a direct probe on 0.1.6 also passed — because that probe ran
*before* the repo's devDependencies moved to 0.1.7. After `pnpm install` put the 0.1.7 closure
in the checkout, the 0.1.6 profile **lost its roster**: the resolution base was the profile,
whose table reaches the linked checkout's own tree, so the probe found the checkout's 0.1.7
`dsh-agent-preset-registry`, disabled the working plural row, and then failed to import
`agent-preset-registry` plus the four `dsh-agent-preset` rows:

```
dsh: warning: 5 entries did not activate
agent-preset-registry (@deepseek-ai/dsh-agent-preset-registry): failed to import
preset-standard (@deepseek-ai/dsh-agent-preset): failed to import
…
```

Two assumptions were wrong: the service (`ctx.pluginPackages`) exists on **0.1.6** as well as
0.1.7, so "absent service" was never the discriminator it looked like; and a resolution probe
answers "can this name be resolved from here", which is not "does this installation ship this
roster" whenever a `link:` can point at a checkout with its own dev tree.

Reading the installation anchor fixed all three lines and is layout-independent. A
`createRequire(installAnchor).resolve(...)` variant is **not**: under a pnpm strict install the
registry is a dependency of `dsh-web-app` and is not natively reachable from the `dsh` package.
The 0.1.6 keyless-smoke leg in the CI matrix is what caught the regression; the direct probe
matrix alone would have shipped it.

### 3.3 The four preset declarations are inlined

On 0.1.7 nothing in an ACP profile would declare a preset, so the bridge must ship the
declarations itself. They are taken from `@deepseek-ai/dsh-web-app@0.1.7-rc.2/presets/*.patch.yml`
(MIT). Row-id diff against the roster's bundled presets shows the web-app set **is** the same
composition plus the 0.1.7 row deltas (`workflow-worker-thread` → `workflow-ptc`, and
`tool-plugin-manager`) — no web-specific rows.

They live **inline in `cordis.patch.yml`** rather than in separate `presets/*.patch.yml` files
listed from `dsh.bundle.patch`: that field is a single path string on 0.1.5
(`join(packageDir, bundle.patch)`), so an array would break the older lines the release
deliberately keeps.

One deliberate deviation from the web-app copy: each declaration gets `name`/`description`
back (from the old roster's per-preset `preset.yml`). 0.1.7's registry publishes no `name` for
a shipped id — its own surfaces localize display copy through `presetDisplayText` — while this
bridge's ACP dropdown and `/preset` render `preset.name ?? preset.id` themselves. Publishing
the copy keeps the labels identical on all three lines. Verified: the `agent_preset` option
lists `standard, ptc, minimal, cordis` on 0.1.5, 0.1.6 and 0.1.7, with no broken row (so the
`cordis` preset's `customSkillDirs` expression, copied verbatim, mounts in an ACP profile too).

### 3.4 One member probe in `lib/`

`resolveMountablePreset(presets, requested)`: call `presets.resolveMountable` when it exists,
otherwise `presets.resolve()` and refuse a row whose `broken` is set. `broken` is the same
discovery verdict both rosters publish, so the refused-here contract is reproduced exactly;
only the error class differs on 0.1.7 (a plain `Error` → internal error instead of the roster's
`agent-preset/*` remote error → invalid params), and a broken preset is a deployment fault
either way.

This is the **only** runtime shape probe added. It is not a generation flag: a host that
republishes `resolveMountable` keeps its own refusal.

### 3.5 Version and pins

- `package.json` → **0.9.1**; every `@deepseek-ai/dsh-*` peer except the retired plural roster
  gains `|| ^0.1.7-alpha.1` (the line's first prerelease).
- `@deepseek-ai/dsh-agent-presets` keeps `^0.1.5-rc.2 || ^0.1.6-alpha.1`: it has no 0.1.7
  release, and the peer gate is satisfied anyway (`^0.1.5-rc.2` reaches 0.1.7-rc.2). Leaving
  it declared is also what keeps the 0.1.5/0.1.6 lines honest.
- devDependencies move to the newest line (`@deepseek-ai/dsh` 0.1.7-rc.2, the rest
  `^0.1.7-alpha.1`), and the plural roster is dropped from devDependencies. pnpm's
  auto-install-peers still materializes `dsh-agent-presets@0.1.6-alpha.2` in the checkout
  (the bridge declares it as a peer); it is inert — nothing in `lib/` imports it, and the gate
  disables its row on 0.1.7. The whole lockfile is regenerated, per the README's standing
  instruction.

## 6. Risks

- **The gate reads a file the CLI owns.** `profileContext.installAnchor` is boot-plane metadata
  from `@deepseek-ai/dsh-app-boot`, reached from a `cordis.patch.yml` expression, which
  `scripts/api-surface-check.mjs` does not scan (it guards `lib/`). It is a read of the
  running CLI's own manifest, so the failure mode is bounded and fail-open: no anchor,
  unreadable file, or unparseable version keeps the `≤ 0.1.6` row, which on a 0.1.7 host is the
  §2.2 degradation rather than a boot failure.
- **Copied preset declarations can drift** from `dsh-web-app`'s. They are pinned to
  0.1.7-rc.2 and the composition is the roster's own, so a future upstream preset edit is a
  bridge change like any other bundled data.
- **Rollback**: revert the release commit. 0.9.0 already handles 0.1.5/0.1.6, and a 0.1.7 host
  degrades to "no roster" (bootable, no `agent_preset`).

## 7. Follow-ups

- **`command-goal` is still not disabled at base level.** The web-app 0.1.7 patch disables it
  (the shipped `standard` preset owns the row), but doing so here was out of scope for this
  migration — it is the pre-existing, documented exception in `cordis.patch.yml`. On 0.1.7 the
  consequence is the same as on 0.1.5/0.1.6: a `minimal`/`code` session still advertises
  `/goal`.
- **If upstream ever publishes `dsh-agent-presets@0.1.7+`** (or republishes a plural roster),
  the gate must be revisited: it currently classifies by installation version, not by package
  presence, so a mixed install would follow the version.
- The **canary** job re-verifies 0.1.7 until upstream publishes a newer line under `alpha`; at
  that point it becomes a real early warning again with no change to the workflow.
- **A future 0.1.x after 0.1.7** is classified as "registry line" by `patch >= 7`. That is the
  upstream direction, but if a later line changes the roster again, the gate needs a new
  boundary rather than another OR term.

## 8. Findings from the first real upgrade (2026-09-25)

The maintainer's live profile was the first non-stock one to boot 0.1.7, and three failure
classes surfaced that no test here could have produced — the first two in the 0.9.1
`feat(compat)` / `fix(doctor)` commits and the third in the `fix(list)` commit, none with a
version bump.

1. **User presets vanish, and a *configured* id then bricks `session/new`.**
   `~/.dsh/.agent-presets/standard-flash/` was discovered by the old roster's
   `includeUserRoot`; 0.1.7's registry scans no directory, so `Unknown agent preset:
   standard-flash` refused every new session. The migration for a user preset is a
   `@deepseek-ai/dsh-agent-preset` declaration row in the profile's user layer — rebased
   onto the new line's row set (`workflow-worker-thread` → `workflow-ptc`) and reading its
   default from `agent-preset-registry.config.default` — and the bridge now keeps a
   *blank* session usable meanwhile (substitute + stderr note), while a session that
   already ran the missing preset still refuses, since the blank-only rule exists to keep
   a transcript from straddling two tool sets. `scripts/compat/public-surface.json` gained
   `agentPresets.defaultId` for that substitute (declared as a getter on both rosters).
2. **A third-party bundle can disappear silently.** `dsh-free-search@0.4.24` imports
   `SettingsProvider`, which 0.1.7's `dsh-settings` replaced with `SettingsForms`; the entry
   failed to import, the loader continued, `web_search` was simply gone, and the doctor
   still printed `RESULT READY`. Two things changed: the doctor promotes the boot's own
   report (`N entries did not activate`, `skipping profile bundle`) into `RESULT DEGRADED`
   with the entry names and exit 1, and the READMEs document the upgrade check
   (`dsh-free-search ≥ 0.4.39` for 0.1.7).

3. **`session/list` stalls on any corpus larger than a scratch home (a third, measured
   class).** The list path asked the persistence layer for one title per stored session,
   and paid `stat(id)` + a full log decode for each. 0.1.7 made both expensive: `stat()`
   folds in `historicalCorpusRevision` (a walk of every generation artifact, stat'd and
   hashed, uncached) for older-format logs, and a log decode costs ~217ms against
   ~9ms on 0.1.5. Measured on the maintainer's own store (274–302 sessions, ~160MB):
   **60s per `session/list`**, against 2.5s on 0.1.5 — past the client's 30s wire timeout,
   so the sidebar never loaded. Fixed without a version bump, in three parts:

   - the size guard and the cache key now come from the single `list()` pass
     (`sizeBytes`, `revision`) instead of a per-session `stat()`;
   - the request path gets a budget (`DSH_ACP_LIST_BUDGET_MS`, default 2.5s) and returns
     what it reached, most recently updated session first;
   - everything the budget missed keeps resolving off the request path and arrives as
     `session_info_update`, converging to full coverage (133/133 titled sessions on the
     real store) with the cache keyed by revision so a re-list is a map lookup.

   Now: 2.7–3.0s per call, 20 of the recency head titled inline on a warm cache, the rest
   pushed as they resolve.

   The regression is invisible to a boot-time smoke test — a scratch `DSH_HOME` has a
   handful of sessions, so even the unbounded version finishes in milliseconds. It is
   pinned instead by `scripts/stored-titles-test.mjs`, an offline unit test over an
   extracted `lib/stored-titles.js` whose dependencies are injectable: the fake's
   `stat()` **throws**, so any return to per-session probing fails the suite, and its
   load counter proves the read count tracks the budget rather than the corpus.

Lesson for the next line: **the boot-time matrix proves the bridge, not the profile.** A
stock composition is what CI can pin; everything a person adds — presets, third-party
bundles — has to be *diagnosable* from the boot's own output, because those are the
failures that do not stop the process. And **a scratch home proves neither**: scale
failures (corpus-sized reads, timeouts past the wire limit) need either a real store or a
unit test that counts the calls.
